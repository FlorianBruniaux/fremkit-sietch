# Google Calendar

Proposed original code under the repository MIT license. Requires Fremkit SDK 1 **and** the core Google OAuth integration, Calendar provider payload contract v1, multi-account `connections` settings and the `connectionService` account guard. SDK 1 alone does not establish provider availability. No external assets, direct network requests or credential access.

Install from a development catalogue after consent. In admin, authorize the Google Calendar read-only services, choose the calendars on each Google connection, and select the intended accounts in the widget's settings. The manifest uses `connectionType: google`, `connectionService: google-calendar` and the `google-calendar:*` channel family; OAuth service grants use the separate `calendar` identifier. There is no default account selection. The iframe never receives OAuth credentials. The existing ICS calendar remains a separate source.

The full agenda shows selected calendars from multiple accounts, with account, calendar label and calendar ID on each row. Account and calendar filters retain exact IDs; duplicate labels or titles cannot collapse identities. Merges ongoing and upcoming events by normalized start timestamp and bounds the full view to 1–30 rows (default eight), disclosing more loaded events and provider truncation. Recurrence actions use the exact instance ID, preserving opaque IDs up to the provider's 1024-character limit without truncation. The provider excludes cancelled events before publishing this contract; no cancellation field is invented in the widget.

Timed events display their supplied IANA time zone, with an explicit unknown-zone label when absent. All-day events display the original date-only `startDate` and exclusive `endDate` directly, without converting them to the browser's local date. The next timed meeting has an in-progress or bounded countdown; an all-day-only agenda is labeled as all-day rather than empty. Known empty is shown only for successfully loaded selected calendars. Errors and stale timestamps stay account/calendar-specific, so a failed calendar does not disable a healthy calendar of the same account. The host remains the authority for action validation.

Event Open requires a fresh selected event advertising `open.available: true` with no unavailable reason. It sends the exact `{ connectionId, calendarId, eventId }` tuple through the selected connection's `open` command. The core re-fetches the event and opens only its validated Calendar HTML-link token using the verified account email. The widget never constructs a URL.

Join is enabled only when the current selected event advertises `join.available: true`, `join.reason: null`, its own calendar is fresh and no more than 120 seconds old, the intended account identity is known and the event has not ended. It sends `Fremkit.sendCommand('google-calendar:' + connectionId, 'join', { connectionId, calendarId, eventId })`. The core refetches and validates the attached HTTPS Meet video destination and reports host opening success; no URL comes from the iframe. Missing or unsupported destinations and stale events have no Join button and retain a visible explanation. Progress and success/failure notices distinguish event opening from meeting opening. Replacement snapshots and account subscription generations suppress late command feedback. Every calendar-filter transition advances a monotonic action revision, so an away-and-back filter sequence cannot revive an old Join result. If a selected calendar disappears or its account data becomes unknown, the filter returns to all selected calendars with an account-specific unavailable notice. The failed account remains visible and healthy selected accounts remain reachable; unknown data is not presented as a loaded zero. Creating, editing and deleting events are outside this package.

Account selection first clears snapshots and feedback, unsubscribes old channels and rejects late callbacks even after reselecting an account. Calendar filters select exact loaded account/calendar tuples. Connection setup and reconnection instructions remain visible. French/English strings, transparent surfaces, theme/accent tokens and navigation slot alignment apply to full and compact views. Frequent full-view controls have at least 56 × 56 px targets and visible keyboard focus. Compact mode is a read-only next-meeting summary, with the intended account/calendar identity; the host controls its full-tile touch popover.

From the registry root, run `pnpm exec vitest run tools/test/google-widgets.test.ts`, then `pnpm test`, `pnpm typecheck`, `pnpm validate`, `pnpm build` and `pnpm check-vendor`. Tests execute the delivered inline script against synthetic snapshots. Real two-account consent, native Meet opening, installed-catalogue behavior and XENEON physical touch remain unverified.
